# Живое демо «НарядAI» — около 7 минут

Используйте два устройства или разные профили браузера: мастер `master / 1234`, исполнитель `worker9 / 1234`. Один профиль использует общую сессию для всех вкладок. Дополнительный исполнитель `worker / 1234` уже имеет активный наряд и очередь.

## Подготовка

1. В папке проекта выполните `docker compose up --build`, откройте `http://localhost:3001` и проверьте `/api/health`. Для телефона используйте адрес компьютера в локальной сети; настройки HTTPS и уведомлений описаны в [README](../README.md). Данные Docker сохраняются в отдельном томе `naryad_data`.
2. Для push используйте HTTPS, включите уведомления в приложении на телефоне исполнителя. На обычном HTTP показывайте только уведомления в открытом приложении и честно называйте режим.
3. Подготовьте два разных собственных снимка демонстрационного оборудования: «до» и «после». Не используйте один файл дважды: проверка обнаружит совпадение. Учебное оборудование должно быть безопасным для съёмки.
4. Выберите режим ИИ заранее: локальные правила работают без ключей; для смысловой и визуальной проверки подключите и проверьте модель до выхода на сцену.
5. Откройте презентацию `docs/presentation.html`. Исторические наряды вымышлены и не содержат фиктивных фотографий ремонта.
6. Заранее откройте PWA на телефоне при работающей сети, дождитесь загрузки и один раз перезапустите её: офлайн-проверка требует уже сохранённой оболочки и авторизованного снимка данных. У каждого демонстратора должен быть отдельный профиль/устройство.
7. В «Оборудовании» откройте насос и скачайте его QR-код **из доступного телефону сетевого/HTTPS адреса**. Ссылка с `localhost` ведёт на сам телефон и для этого не подходит. Проверьте переход штатной камерой заранее.
8. Проверьте RU/ҚАЗ на экране входа и в навигации. Названия оборудования, записи работников и серверные заключения сохраняют исходный язык. Не представляйте переключатель как автоматический перевод производственных данных.

## 0:00–0:40 · Обзор смены

Мастер открывает панель. Покажите текущие активные/проверяемые наряды, выдачу и исполнение за смену в подписях, просрочки, оборудование и статусы сотрудников. Откройте один активный наряд: видны задание, приоритет, срок и «Журнал наряда». Затем откройте общий раздел «Журнал действий»: видны автор, время, действие, комментарий и переход к исходному наряду.

Фраза: «Мастер видит смену в одном окне. Просрочка подсвечивает действующий наряд, сохраняя его рабочий статус».

## 0:40–1:40 · Аварийное задание

Нажмите «Выдать наряд». Выберите насос, например «Насос оборотной воды НВ-2», внеплановый тип, аварийный приоритет и исполнителя без текущей работы. Для заранее открытого аккаунта `worker9` это Тимур Сагындыков. Если его статус изменился во время репетиции, выберите другого свободного слесаря и войдите под соответствующим `workerN`.

Описание: «Обнаружена течь на фланцевом соединении насоса НВ-2. Восстановить герметичность и проверить соединение при контрольном запуске». Приложите фото до, установите срок и выдайте наряд. Покажите состояние исполнителя и рекомендацию системы, если она отображается.

Можно начать со сканирования подготовленного QR насоса: откроются его карточка и история, а мастер выдаёт наряд для выбранного оборудования. Покажите подсказку шифра/норматива и подбор по специальности, занятости и рейтингу на типе машины. Голосовой ввод демонстрируйте только после проверки микрофона и Speech Recognition в этом браузере.

На телефоне исполнителя откройте уведомление, нажмите «Принять в работу» → «Начать исполнение». На экране мастера статус обновляется без ручной перезагрузки.

## 1:40–2:20 · Очередь и срок

Мастер выдаёт тому же исполнителю второе небольшое задание, например осмотр крепежа, со сроком через 1–2 минуты. Исполнитель выбирает «Поставить в очередь».

Пока идёт следующий шаг, срок второго задания истекает. Уведомление получают исполнитель и выдавший наряд мастер. Откройте его и покажите причину внимания. Для репетиции можно заранее создать задание с коротким сроком; не меняйте системное время компьютера.

## 2:20–3:30 · Отчёт и приёмка

По первому наряду исполнитель нажимает «Исполнено» и заполняет отчёт:

- Работы: «Заменена прокладка фланцевого соединения, восстановлена затяжка крепежа. После контрольного запуска течь отсутствует, соединение осмотрено».
- Шифр: подходящая неисправность из справочника.
- Материалы: соответствующая прокладка, 1 шт., либо фактически использованные позиции.
- Фото после: новый снимок результата, отличный от исходного.

Для показа устойчивости отключите сеть **на телефоне исполнителя**, оставив сервер включённым. Заполните отчёт и добавьте фото: приложение сохраняет текст и сам файл на устройстве. Перезагрузите PWA, откройте исполнение и покажите восстановленный снимок. Нажмите отправку: отчёт появится в очереди на устройстве. Верните сеть — произойдут загрузка фото и сдача без повторного заполнения. Для обычного семиминутного показа этот шаг лучше отрепетировать заранее или вынести в дополнительную минуту вопросов.

После отправки откройте журнал: «Исполнено» → «Проверка ИИ». Покажите проверки, балл, замечания и название провайдера. При локальных правилах произнесите: «Сейчас проверяются комплектность и формальные признаки. Для содержательного сравнения подключается модель; визуальная приёмка остаётся за мастером».

Мастер принимает работу. При необходимости изменяет балл с комментарием. Только после этого наряд становится закрытым. Кнопка PDF в карточке открывает печать полного отчёта: реквизиты, работы, материалы, фото, все проверки и хронология включаются независимо от выбранной вкладки. В диалоге браузера выберите «Сохранить в PDF».

## 3:30–4:30 · Некачественный отчёт

Создайте третье задание по гидравлике и назначьте исполнителю, который завершил первую работу. Примите и начните его. Отправьте отчёт с описанием работ, но **без фото после**, добавив масло в количестве более чем вдвое выше указанного справочного расхода.

Отсутствие фото не должно блокировать показ проверки: исполнитель видит предупреждение и отправляет отчёт для анализа. Система ставит «Требует доработки», указывает отсутствие фото и отклонение по материалам. Покажите кнопку возврата в работу. После повторной отправки прежний отчёт и проверка сохраняются как предыдущая попытка. Мастер не может закрыть наряд до прохождения контроля.

## 4:30–5:30 · Отчёт и рейтинг

Откройте «Аналитика и отчёты», выберите смену или нужный период. Покажите сводку, рейтинг, вклад качества, сроков, доработок, объёма и отказов. Оценка мастера замещает рекомендацию ИИ.

Скачайте Excel или откройте печать отчёта. В Excel покажите листы с событиями, рейтингами и расходом ТМЦ. Уточните, что затраты времени на приёмку мастером не ухудшают показатель своевременного исполнения. Выберите один участок и покажите, что показатели качества и своевременности относятся к этой выборке.

На панели руководителя покажите среднее время реакции и исполнения с количеством наблюдений, расчётный простой и топ оборудования/людей. При отсутствии измерений показывается отсутствие данных, а не нулевое время. В уведомлениях мастера/руководителя доступна еженедельная статистическая сводка за предыдущую полную неделю; она формируется один раз на период и не требует внешней модели.

Сравнивайте сотрудников в роли мастера: личный рейтинг рабочего строится только по его доступным нарядам. Список работ отбирается по дате выдачи, исполнение — по дате сдачи, а рейтинг — по дате закрытия; эти количества не обязаны совпадать.

## 5:30–6:30 · Закономерности за три месяца

Выберите период за три месяца. Покажите фактические примеры из истории:

- Повторный ремонт подшипникового узла конвейера К-3: рекомендована проверка соосности и смазки.
- Повышенный расход гидравлического масла: требуется сверка причин и нормативов.
- Внеплановые неисправности после ППР: проверка качества обслуживания.
- Частые возвраты на доработку: разбор причины, сложности и условий работы.

Подчеркните: рекомендации вычислены по нарядам; корреляция не означает установленную причину.

Дополнительно покажите зависимости дневной/ночной выдачи и групповые повторы, если выборка действительно дала сигнал. Раннее предупреждение роста сравнивает два равных недавних окна по 7–14 дней. Оно появляется только при достаточной выборке и заметном росте; это сигнал для диагностики, **не предсказанная дата или вероятность поломки**. На малом/спокойном наборе отсутствие такого предупреждения корректно; не подменяйте данные ради демонстрации.

## 6:30–7:00 · Завершение

Покажите мобильный интерфейс, переключите RU/ҚАЗ, вернитесь к русскому и откройте финальный слайд. Сформулируйте следующий шаг: пилот на одном участке, измерение скорости выдачи и простоев, подключение согласованной модели и интеграция с ERP.

Не обещайте жюри готовый прогноз отказа или полную визуальную проверку, если сервер работает в `demo-rules`. Исходный кейс выделяет 25 баллов качеству ИИ; для претензии на максимум нужна настоящая проверенная модель, а также живой сценарий на физических телефонах. Полная матрица и состав сдачи — [REQUIREMENTS.md](REQUIREMENTS.md).

## Запасная видеозапись до 3 минут

Обновлённая 8 октября 2026 [резервная запись](../artifacts/demo.webm) длится **104,68 секунды — примерно 1 мин 45 с**. В ней показаны реальные действия в собранном приложении:

| Время | Содержание |
|---|---|
| 0:00 | Панель смены мастера |
| 0:09 | Выдача планового наряда свободному исполнителю |
| 0:20 | Вход исполнителя `worker9`, внутреннее уведомление, принятие и начало |
| 0:30 | Отчёт: работы, шифр и подтверждение отсутствия расхода ТМЦ |
| 0:38 | Проверка отчёта и объяснение оценки |
| 0:46 | Решение мастера и закрытие наряда |
| 1:00 | Общий журнал: авторы, время и изменения |
| 1:04 | История оборудования и QR-код; затем переключение RU/ҚАЗ |
| 1:15 | Аналитика за три месяца и обнаруженные закономерности |
| 1:30 | Рейтинг исполнителей и его составляющие |

Запись без озвучки, на изолированных учебных данных в явно обозначенном режиме `demo-rules`. Офлайн-отчёт с фотографиями, проверка содержания фото настоящей LLM и доставка фонового push на физическом телефоне **этим роликом не подтверждаются**. Их следует отдельно проверить и показать вживую.

[Метаданные](../artifacts/demo-metadata.json) содержат точную длительность и временные отметки глав. Для новой записи выполните `npm run build` и `npm run record:demo`; потребуется установленный Edge и компонент FFmpeg для Playwright. Сценарий использует отдельную временную базу и не меняет обычный стенд. Для выступления также готова [презентация PDF на 10 страниц](../artifacts/presentation.pdf).

## Если что-то мешает демо

| Симптом | Действие |
|---|---|
| Нет фонового push | Проверить HTTPS, разрешение браузера, подписку, сеть; показать внутреннее уведомление с честным пояснением |
| «Версия изменилась» | Обновить карточку и повторить действие по текущему статусу |
| Конфликт у офлайн-отчёта | В очереди нажать «Вернуть в черновик», открыть исполнение, проверить изменения, подтвердить текущую версию и отправить снова. Фото сохраняются; исходная версия автоматически не подменяется |
| Офлайн-отчёт не отправился | Открыть приложение под тем же исполнителем, проверить сеть и очередь. После восстановления доступности повторная отправка защищена от дублирования requestId |
| PWA не открылась без сети | Проверить доверенный HTTPS и предварительную загрузку Service Worker/оболочки; обычная впервые открываемая HTTP-ссылка не является офлайн-стендом |
| QR ведёт не туда | Перегенерировать из адреса, доступного телефону. localhost на компьютере и телефоне — разные устройства |
| Нельзя начать новый наряд | Завершить или приостановить уже выполняемый, показать очередь |
| Модель недоступна | В отчёте будет отмечен переход на локальные правила |
| Фото вернулось на доработку | Сделать новый снимок; не повторять файл «до» |
| Нужен новый набор данных | Для отдельного стенда Docker использовать другое имя проекта, например `docker compose -p naryad-demo up --build`, предварительно остановив основной стенд; его том сохранится. Для локального npm-запуска указать новый пустой `DATA_DIR` |
