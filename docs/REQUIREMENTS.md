# Сверка с требованиями кейса

Это матрица реализации прототипа, а не утверждение о пройденных производственных испытаниях. Исходный кейс: «НарядAI» АО «Костанайские минералы». Особое правило из схемы: **каждый исполненный наряд проходит проверку; окончательно закрывает мастер**.

| Блок | Реализация | Ограничение / способ проверки |
|---|---|---|
| Роли | Мастер, исполнитель, руководитель, администратор; авторизация и серверные проверки | Демо-PIN, сессии; производственное управление учётными записями расширяется отдельно |
| Выдача | Обязательные реквизиты, оборудование по участку, исполнитель/бригада, срок, приоритет, фото, комментарий | «До минуты и 6 нажатий» зависит от выбранного шаблона; требуется замер на телефоне |
| Статусы сотрудников | Свободен, занят, очередь, не на смене | Статусы рассчитываются из текущих нарядов и признака смены |
| Панель мастера | Карточки, канбан/список, фильтры, счётчики | Обновление через SSE и резервный опрос; задержку измерять на целевой сети |
| Жизненный цикл | 10 статусов схемы, дополнительная отмена мастером, журнал автора и времени | Переходы проверяются API; прямое закрытие исполнителем запрещено |
| Отказ и пауза | Причина обязательна | Переназначение выполняет мастер |
| Завершение | Работы, шифр, материалы и количество либо явная отметка об их отсутствии, фото, комментарий | Неполный отчёт допускается на проверку для сценария доработки; это не приёмка |
| Проверка выполнения | Асинхронный отчёт, вердикт, балл, причины, доработка; решение мастера | Без модели работает явно обозначенный `demo-rules` |
| Смысловое соответствие | Подключаемая совместимая LLM | Для полной смысловой проверки требуется доступная и проверенная модель |
| Фото | Сжатие JPEG, контроль загрузок, хеши повторений, заявленные даты | Нет доказательства подлинности или времени съёмки; визуальное сравнение требует мультимодальной модели |
| Сроки | Фоновый контроль, порог напоминаний и повторов | Исполнение останавливает рабочую просрочку; доработка вновь активна |
| Уведомления | Внутренние события и Web Push по подписке | HTTPS, разрешение пользователя и доступ к push-службам; звук контролирует ОС |
| Отчёт по наряду | Карточка, события, работы, материалы, фото, ИИ, оценка мастера; предыдущие попытки сохраняются при повторной сдаче и переназначении | Исторические снимки не подделываются; в учебном архиве фото отсутствуют |
| Отчёт смены | Выдано/исполнено/просрочено, загрузка, сводка | Смена 08–20 или 20–08, `Asia/Qyzylorda` |
| Рейтинг | Пять прозрачных компонентов, периоды, сотрудники/бригады | Учитывает закрытые наряды; повтор за 7 дней относится к предыдущему ремонту |
| Справочники | Участки, оборудование, сотрудники, бригады, шифры, материалы, нормативы; добавление и редактирование, включая признак смены сотрудника | Управление только администратором; удаление и промышленный импорт не реализованы |
| Тестовые данные | ≥550 нарядов, ≥90 дней, ≥4 участка, ≥25 машин, 15 рабочих, 3 бригады, ≥20 шифров, ≥40 материалов | Полностью синтетический набор; даты привязаны к первому запуску |
| Аналитика | Повторы, материалы, отказы после ППР, доработки, динамика | Статистические сигналы; не доказанные причины и не обученный прогноз отказа |
| Простои | Пересекающиеся интервалы объединяются по оборудованию и ограничиваются периодом, включая начавшиеся до него ремонты | Расчётная оценка без датчиков остановки/пуска; обозначается как таковая |
| Экспорт | Excel с карточками, событиями, оценками, рейтингами, ТМЦ и простоем; полный отчёт по наряду печатается из любой вкладки карточки | PDF сохраняется средствами браузера; не отдельный серверный сервис PDF |
| Плохая связь | Кеш последнего состояния, отложенные переходы статусов | Отчёты с фото требуют связи; конфликт версии требует повторного действия после обновления |
| Голос | Возможен браузерный ввод при поддержке API | Зависит от браузера; не автономная серверная транскрибация |
| Ассистент | Ответы на типовые вопросы по данным базы | Явно обозначенный статистический режим, не универсальный диалоговый агент |
| Исходники и запуск | `docker compose up --build`: приложение и SQLite в одном сервисе, постоянный том данных; также доступен локальный npm-запуск на Node.js 24, README, контракт, тесты | Нужен работающий Docker с Compose; публичный репозиторий и хостинг выбираются отдельно |

## Правила жизненного цикла

1. Выдан → принят, в очередь или отклонён.
2. В очереди → принят или отклонён.
3. Принят → в работе.
4. В работе → приостановлен; приостановлен → в работе.
5. В работе → исполнено → проверка ИИ. Оба перехода сохраняются в истории.
6. Отрицательная проверка → на доработку → в работе → повторное исполнение и проверка.
7. Проверка с готовым отчётом → закрыт только решением мастера; мастер может вернуть на доработку или уточнить оценку.
8. Отмена и переназначение — отдельные действия мастера с записью в журнале.

`Просрочен` — признак активного наряда, а не одиннадцатый рабочий статус. Проверка и ожидание мастера не добавляются к длительности исполнения. При доработке контроль исходного срока возобновляется, пока мастер не изменит срок с записью в истории.

## Формула рейтинга

`R = 0,40 × качество + 0,25 × в срок + 0,20 × с первого раза + 0,10 × объём + 0,05 × обоснованные отказы`, каждый компонент находится в диапазоне 0–100.

Качество — средний итоговый балл 1–5, переведённый в проценты. В срок — доля работ, исполненных до срока, по времени исполнения, не приёмки. С первого раза — доля без возвратов и без того же дефекта на том же оборудовании в следующие 7 дней. Объём учитывает норматив и аварийность, нормируется к максимуму выбранной группы. Отказы оцениваются по записанным причинам; отсутствие причины или явно произвольный отказ снижает компонент, производственная причина сама по себе не штрафуется. Критерии допустимости отказов перед реальным внедрением должен утвердить заказчик.

Личный рейтинг исполнителя рассчитывается по доступной ему истории собственных нарядов. Он не заменяет сравнительную таблицу предприятия: объём зависит от выбранной группы, а повторный отказ в чужом наряде исполнителю недоступен. Сравнивать сотрудников следует в роли мастера или руководителя при одинаковых фильтрах. Сводка считает выдачу, исполнение и приёмку по собственным датам событий; переходящий со вчерашней смены наряд входит в сегодняшнее исполнение.

## Проверки перед защитой

- Запустить `docker compose up --build`, открыть `http://localhost:3001` и проверить `/api/health`. Остановка `docker compose down` сохраняет данные Docker в томе `naryad_data`.
- `npm test`, затем `npm run build` и `npm run test:e2e`; тесты домена включают граничные случаи, фильтры периодов и поиск закономерностей в seed. Браузерные тесты используют отдельную временную базу.
- Пройти сценарий [DEMO.md](DEMO.md) на двух независимых сессиях.
- Измерить скорость выдачи, задержку статуса и время загрузки фото на Android.
- Проверить Web Push при свёрнутом приложении и разрешённом уведомлении.
- Проверить модель на реальных обезличенных примерах «до/после» и показать уровень уверенности.
- Проверить на устройстве защиты готовые [презентацию PDF на 10 страниц](../artifacts/presentation.pdf) и [резервное видео длительностью 1 мин 55 с](../artifacts/demo.webm); запись можно обновить командой `npm run record:demo`.

## За рамками готового прототипа

Развёртывание на публичном сервере, подтверждённая работа на конкретных телефонах, интеграции 1С/ERP/ТОиР, телеметрия фактического простоя, промышленная отказоустойчивость, аудит производственной безопасности, казахская локализация и обученный прогноз отказов требуют отдельной работы. Базовый контур хранит данные локально; для масштабирования предусмотрено разделение клиента, API и доменной логики, но миграция на PostgreSQL пока не выполнена.
